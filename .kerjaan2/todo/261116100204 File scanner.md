## Background

The scanner reads the application's TypeScript files and produces the metadata of every component, without ever importing or running those files. It is the only part of the framework that uses the TypeScript parsing library.

## Request

Provide the scanner described in `CLAUDE.md` sections 4.2 to 4.5, using the marker reader for the JSDoc text. For a directory and an optional list of allowed additional marker names, it returns every component's metadata with where it lives (file path and function name), plus the list of all mistakes found. It never stops at the first mistake. It reads only the names of return types and parameter types, never their definitions (`CLAUDE.md` section 2).

## Done when

- [ ] Tests on temporary directories show the valid cases: the component name is the return type exactly as written, including a dotted name such as `winston.Logger`; dependencies follow the parameter order; additional markers are kept with their data in the order written; files in nested folders are found.
- [ ] Each mistake of `CLAUDE.md` section 4.2 has a test, and its message names the function or type at fault: not exported, no return type, more than one main marker, a parameter without a type, two functions returning the same type name.
- [ ] Each rule of section 4.4 has a test: data on `@Config` or `@Action` is a mistake (including a leftover `{"readTypeArguments": true}`), `@Wrapper` accepts no data or `{"ordinal": <integer>}`, and anything else on `@Wrapper` (a non-integer ordinal, an unknown key, plain text) is a mistake.
- [ ] Section 4.5 has tests: with a list of allowed names, an additional marker outside it (such as `@Transction`) is a mistake naming the marker and the function; without a list, every additional marker is accepted. Invalid JSON in a marker is a mistake in both cases.
- [ ] Functions that are not components are left alone without a mistake: no main marker, a nested function, an arrow function or a class method carrying a marker.
- [ ] One fixture with several different mistakes returns all of them in one scan.
- [ ] A fixture file that throws at module level is scanned without that throw happening.
- [ ] `ts-morph` is imported by the scanner only, and every test removes its temporary directory.

## Out of scope

Missing dependencies, cycles and kind rules; importing application files; instantiation.

## Assumptions
- A1 [unseen] Files are scanned in sorted path order and functions in source order, so the result is the same on every machine; all **/*.ts under the directory are read, with no exclusion of test or declaration files
  Why: CLAUDE.md 4.2 says all **/*.ts without exceptions; a fixed order keeps messages and creation order reproducible
  If wrong: add an exclusion or change the sort in src/scanner.ts
- A2 [unseen] On @Wrapper an empty object {} is a mistake, the same main marker written twice on one function counts as more than one main marker, and a negative integer ordinal is valid
  Why: CLAUDE.md 4.4 allows only no data or {"ordinal": <integer>}, and 4.2 says exactly one main marker
  If wrong: relax the check in src/scanner.ts
- A3 [unseen] A function without a main marker is not examined further: its additional markers and any invalid JSON in its JSDoc are not reported
  Why: CLAUDE.md 4.2: only a function with a main marker is a component; the ticket says non-components are left alone without a mistake
  If wrong: report markers on non-components in src/scanner.ts
